# Lifecycle Readiness Condition Contract (2026-08-05)

- **Context**: Phase 5 item 11 (advisory planning readiness checklist) needed a condition schema that item 12 (completion review) and item 19 (enforcement) can reuse without inventing a second shape.
- **Change**: `@eridu/api-types/shows` now exports `LIFECYCLE_READINESS_PHASE` (`planning_readiness` | `completion_review`), `LIFECYCLE_CONDITION_STATUS` (`met` | `not_met` | `not_applicable`), `lifecycleConditionSchema` (`{key, label, status}`), and `showPlanningReadinessSchema` (item 11's concrete phase). Item 12 should define `showCompletionReviewSchema` alongside it using the same enums and a `completion_review` phase literal — not a parallel shape.
- **Backend home**: `apps/erify_api/src/show-orchestration/planning-readiness.service.ts` (`PlanningReadinessService`) computes item 11's five conditions from an **explicit show-id list**, not a re-derived date window — it does not depend on `ShiftAlignmentService`'s planning-window/operational-day logic. Item 12's completion checklist should follow the same shape: a capability service in `show-orchestration` taking explicit show ids, not a new date-scoped query.
- **Shared task-coverage util**: `apps/erify_api/src/show-orchestration/show-task-coverage.util.ts` holds `computeShowTaskCoverage`/`mapTasksByShowId`/`isModerationTask` — both `ShiftAlignmentService` (planning-risk warnings) and `PlanningReadinessService` (task-stage/task-assignment conditions) import from here. Do not reimplement required-task-type or moderation-detection logic a third time; extend this util instead.
- **Routes**: `GET /studios/:studioId/shows/:id/planning-readiness` (single) and `GET /studios/:studioId/shows/planning-readiness?show_id=...` (bulk-by-ids, capped at `PLANNING_READINESS_MAX_BULK_SHOW_IDS` = 100, exported from the service and imported by the DTO schema — one constant, not two).
- **Frontend consumers**: show-detail Planning Readiness card, and a per-row column on `/task-setup` scoped to the current table page's show ids (not the whole date-range scope). `ShowReadinessTriagePanel` / `show-readiness.utils.ts` were deliberately left untouched — they stay a task-only display fed by `ShiftAlignmentService.task_readiness_warnings`, not the readiness authority.
- **Reference**: `.agents/skills/show-production-lifecycle/references/state-gates.md` § draft → confirmed, and `docs/roadmap/PHASE_5.md` item 11.
